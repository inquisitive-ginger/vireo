Design exploration · auto-bug #129 · 2026-09-03

A recipe link on a planned meal

One field, four decisions. The spec's "no recipe bank" position is not up for review — this adds a link, not a model: no scraping, no ingredient parsing, no thumbnails. needs still carries what the store trip requires. What has to be settled is where the cook reaches it, because the meals surfaces are deliberately spare and every one of them is already full.

“It'd be great if it was possible to add a recipe URL to the meal record”

Dad, tier 4 · reported in-app from /meals · report cfc58841

Decision 1 — the affordance on the /meals row

The week page is calm and its row is full: title · sides on line one, avatar · verb · try bite on line two, actions trailing. Three candidates, sheet 02.

Decision 2 — the wording

A generic “Recipe”, or the source stated (“seriouseats.com”). The house voice states specifics — “3 things needed”, “Bakery · all 2 in the cart” — but a domain is longer and competes with the try bite. Sheet 03.

Decision 3 — does the Tonight widget carry it

The fridge is where the cook actually stands at 5pm. It is also the one surface whose whole tile is already a link to /meals. Sheet 04.

Decision 4 — which kinds get the field

Cooking only, or cooking + takeout (a takeout link is a menu, and “Where from? → the menu” is the same one-tap need). Sheet 05.

Settled without a gate — say so if you disagree

A new nullable recipe_url column, not the dormant notes field. notes is free text plumbed through the API and rendered nowhere; overloading it would mean parsing a URL back out of prose, which is the parsing problem the spec deleted on purpose.

http/https only, validated by a shared Zod schema, opened with target="_blank" rel="noopener noreferrer". The row link is z-lifted above ItemCard's activate overlay — the same recipe the widget already uses for its claim button.

02Decision 1

The /meals row — three ways to reach it

Each option is rendered on the real row, twice: a roomy meal (short title, no try bite) and a crowded one (long title, sides, try bite, an unclaimed day's claim button). The crowded render is the honest one — it is what Thursday actually looks like.

Option A

The title carries it

No new element at all. A meal with a recipe underlines its own name; tapping the name opens it, tapping anywhere else still edits.

Cost: tapping a title means two different things depending on data, and the row's tap-to-edit target quietly loses its best part. Nothing tells you which rows have one until you look for underlines.

04Decision 3

The fridge — does Tonight carry the link

This is the decision that decides whether the feature is used. The cook is standing at the fridge at 5pm; the alternative is two taps (tile → row). Against that: the whole tile is already one link to /meals, the card has two audiences and a hairline that separates them, and every control added here has to be z-lifted out of the overlay.

Reach i

The widget stays spare

Nothing changes on the fridge. The tile deep-links to the week, and the row there carries the link — two taps, and the second one is on the surface that already holds every other meal detail.

Keeps the card's promise: above the hairline is what a kid reads at 3:30, below it is the adult glance. A recipe link is neither.

05Decision 4

Which kinds get the field

The drawer reshapes per kind and unused fields submit null. Cooking obviously gets it. Takeout is the live question: a link on a takeout meal is a menu, and “Where from? → the menu” is the same one-tap need with a different word. Leftovers and going out get nothing either way.

Cooking only

Matches where sides, try bite and needs already live. One label, one helper, one word on the row — nothing to disambiguate.

The request said “recipe”, and this answers exactly it.

06Ledger

What this deliberately is not

spec.md §“Why there is no recipe bank” is the standing decision and this does not touch it. Every line below is a thing a recipe URL invites and that this story refuses — recorded here so a later session does not rediscover them as ideas.

✕ Fetching the page No title, no image, no favicon, no oEmbed. The Pi would be making outbound requests on a family's behalf, and a dead link would start rendering as a broken thumbnail instead of a word.
✕ Parsing ingredients into needs The exact problem the free-text needs field exists to delete. The planner types what the trip needs; the recipe link is for the stove, not the store.
✕ A recipe library or reuse No “meals you've cooked before” list, no autocomplete off past URLs. That is a recipe bank with extra steps, and it is deferred in progress.md on purpose.
✕ More than one link One nullable column, one link. A second one is a list, a list is a model, and the model is the thing we are not building.
✕ An offline copy Opening the link needs the internet; the app does not. The SW story (M5/7) is about the grocery list in an aisle, not about caching third-party recipe pages.
✕ Reusing notes Dormant, free-text, and rendered nowhere. Storing a URL in it means parsing one back out, and it would strand whatever notes is eventually for.
