# 2026-08-14 — fix, auto-bug #107 (plugins crash on stale clients)

**Report:** `18381226` — "Plugins not loading as expected", family profile,
/calendar, Android. Ring buffer: `Failed to fetch dynamically imported module:
…__federation_expose_Plugin-D9oMOgw_.js`.

**Root cause:** prod served every file with **no `Cache-Control` header**, so
browsers applied heuristic freshness (~10% of time-since-Last-Modified) to
mutable stable-URL files. The phone's `remoteEntry.js` was cached from the
**Aug 11 build** (verified: the `3d6cbc4` web image on the Pi serves exactly
`D9oMOgw_`) and survived two deploys and every reload, importing hashed chunks
those deploys had deleted → `PluginErrorBoundary` on any plugin detail view.
Looked mobile-specific only because the phones were the devices nobody had
hard-refreshed; dev at phone width rendered all plugin pages clean.

**Fix (PR #108, `apps/shell/Caddyfile`):** `sw.js`, `manifest.webmanifest`,
`*/remoteEntry.js`, and the SPA document → `Cache-Control: no-cache`
(revalidate always — ETag 304s keep it cheap); content-hashed bundles under
`/assets/` → `immutable`. Validated with `caddy adapt` against the prod web
image before merging.

**Also this session (same day, before the report):** prod outage triaged —
the USB SSD browned out off the bus 21:27 Aug 13; recovery = reseat + fresh
`compose down/up` (stale containers SIGBUS on the dead mount instance;
recipe now in auto-memory). Postgres WAL-recovered, zero loss.

**One-time client step:** phones whose cached copies predate the header need
a single site-data clear (or the heuristic to lapse) — the server can't
invalidate what it already handed out.
