**Date:** 2026-06-15
**Type:** Product

## What was decided

### Q1: Recurrence deferred

One-shot tasks only in M2. Recurrence is scheduling infrastructure, not completion flow, and risks bloating the milestone past the done-line. Deferred to a future story (M2+ or standalone).

### Q2: XP surfacing — running total, no levels

XP is awarded on completion and stored as a cumulative per-profile total (`xp_balances` table in `chore_engine` schema). The total is displayed in the chores full-page view (`text-metric` treatment) and in the today widget large size (`text-card-title`). No levels, progress bars, badges, or leaderboards in M2.

### Q3: No approval step — completion is auto-accepted

Completed tasks move directly to `completed` status. No `awaiting_approval` column or state. The parent notification is the visibility mechanism ("a parent sees it happen"). Instant positive feedback for kids was the deciding factor.

**Data model consequence:** `tasks.status` enum is `pending | completed` only in M2. No intermediate states.

### Q4: One assignee per task; tier 4 assigns, tier 1+ completes

- `assignee_id`: single UUID FK, required at creation time (no unassigned tasks)
- Tier 4 creates and assigns to any profile
- Tiers 1–3 cannot create tasks (can only complete their own)
- Self-assignment for tier 3 (teen propose flow) is deferred to M2+

### XP Award + Parent Notification combined

Both stories are small event subscribers on `chores.task.completed`. Combined into one dev session (`dev-chores-xp-and-notification`) to avoid a trivially small standalone session.

## What the next session needs to know

- **M2 Design: Chores is first** — all five dev stories depend on it. The design session must produce visual direction for: kid task list, parent task list, create-and-assign surface, completion interaction, XP display, and widget (standard + large).
- **`chores.task.completed` payload shape** is fixed: `{ taskId, assigneeId, xpReward, completedAt }`. Both the XP subscriber and notification subscriber rely on this — do not change the shape without updating both subscribers.
- **`chores.today-summary` widget id** must match the reserved layout seed exactly (ADR 028). If the id doesn't match, the placeholder card won't be replaced.
- **Parent notification**: the subscriber needs to look up the assignee's name (not in the event payload, only `assigneeId`). Check the platform profiles API for the lookup pattern.
- **XP + Notification dev session**: these are combined. The session kickoff references both story specs.
