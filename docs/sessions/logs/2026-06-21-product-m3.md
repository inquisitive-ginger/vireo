# Session Log — M3 Product Planning: Calendar

**Date:** 2026-06-21
**Type:** Product (planning)
**Opened by:** a requirements **brainstorm** against the family's real paper wall
calendar (the user shared a photo of the current month and described their workflow).

---

## What was decided

The session opened, at the user's request, with a requirements brainstorm before
the formal story breakdown. We read the family's analog system from the photo and
the user's notes, then settled the MVP shape through two rounds of option gates.

**Reading the paper calendar (requirements mined):**

- The **recurring activity backbone** dominates — nearly every weekday is a standing
  commitment (T&T @5:15, gymnastics @4:45, speech @5, basketball, vision @4:45,
  karate @9). One-offs are the minority. This is the big divergence from Chores,
  which deliberately had no recurrence; Calendar can't skip it.
- **Color = person** — the highlighter coding is exactly ADR 030 member identity
  colors. The digital twin maps to it 1:1.
- **Multi-day spans are first-class** — the "→" arrows (Zach to London, FISW camp,
  to Brighton) are spanning events, not single days.
- **Tracking is woven in** — the "T. antibiotics ✓✓✓" daily-checkmark run is a
  streak/course closer to chores/health than to events; left **out** of MVP.
- **The pain is notifications** — appointments are duplicated into Google Calendar
  "mostly to capture the notification aspect." So the "separate calendar" being
  retired is really a notification engine. The paper already wins on glance and on
  the main user's comfort (she prefers paper, is a self-described technophobe).

**Strategic frame:** augment, don't replace. The tablet is a **glanceable twin** of
the paper; the system earns its keep on what paper can't do — hold recurrence
reliably, capture from a phone, and remind. The done-when ("family stops using a
separate calendar for day-to-day scheduling") is only reachable if capture +
reminders ship, since notifications are why Google persists.

**Settled (via gates):**

| Question          | Decision                                                                                            |
| ----------------- | --------------------------------------------------------------------------------------------------- |
| Center of gravity | **Glanceable tablet mirror** leads; mobile capture + reminders ship alongside                       |
| Tablet frame      | **Month** default (mirrors paper); truncate crowded days; drill to week/day                         |
| Recurrence        | **Simple weekly repeat** + end date; per-occurrence edits/skips deferred                            |
| Activity tracking | Recurring **activities first-class** ("Tuesdays are tumbling"); no per-occurrence attendance/streak |
| People model      | **One shared calendar**; **one owner per event** (identity hue) **+ a Family tag**                  |
| Event shape       | All-day **and** timed; **multi-day spans** first-class                                              |
| Email surfacing   | **North star** — `suggested`/`source` model reserved now; parsing build deferred                    |
| Authorship        | **Tier 4 creates/edits**; tiers 1–3 view; teen propose-flow deferred (mirrors chores)               |
| Home widget       | `calendar.up-next` — **family** framing on the shared tablet, **mine** on personal/mobile           |

## Stories defined

`docs/modules/calendar/` stood up (spec + progress board + 8 dependency-ordered
story specs). Stories 1–7 are M3 MVP; #8 is the deferred north star (model lands in
#1).

1. **Event Model + Plugin Scaffold** — `calendar` plugin; `events` table; weekly
   recurrence; owner/Family; all-day/timed/multi-day; CRUD API; events + permissions
   namespaces. _Gated by the recurrence-storage owed ADR._
2. **Tablet Month View** — the hero glanceable mirror; color-by-owner; truncation;
   drill to week/day.
3. **Event Create / Edit** — one reused drawer (owner/Family, time, weekly repeat,
   span); tier 4.
4. **Mobile Event Creation** — the create form on the mobile PWA + a mobile read
   surface; unifies capture.
5. **Recurring Activities** — recurring series surfaced/managed as named Activities
   (`is_activity`).
6. **Event Reminders** — time-based reminders via `platform.notify()` + Web Push.
   _Gated by the reminder-scheduling owed ADR._
7. **Up Next Widget** — `calendar.up-next` (family + mine framings, sizes, empty
   states); fills the reserved slot.
8. **Suggested Events Inbox** — _deferred north star_; email/newsletter parsing into
   `suggested` events. _Gated by the external-ingest owed ADR._

## Open questions raised

Logged as **owed ADRs** in the queue (architecture is not improvised in a product
session):

1. **Recurrence storage model** — materialized `occurrences` vs. computed-on-read;
   where exceptions attach; activity-as-table vs. `is_activity` flag. _Gates #1._
2. **Time-based reminder scheduling** — how reminders fire given the in-process
   `EventEmitter` bus (ADR 008) has no timer/cron; durability across restarts.
   _Gates #6._
3. **External-ingest / suggested-events extension point** — source-agnostic contract
   for landing `suggested` events (email first, iCal/Google later). _Gates #8._
