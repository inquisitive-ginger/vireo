# 2026-07-31 — fix session: auto-bug #94 (a person's count included the offer board)

Ad-hoc fix session per `docs/fix-it-playbook.md`; no kickoff existed, none written
(single-issue triage-to-merge, this log is the artifact).

## The report

Zoë (tier 3, report `a59e6e5c`, issue #94, route `/`): _"A specific user's chore
count should only consider ones explicitly assigned to them and not ones that are
still up for grabs."_

## Root cause

Not a new defect — an unfinished rollout. `GET /chores/tasks` hands a taskee
their own rows **and** every unassigned one in a single list, so each surface has
to split it. Gate D6 (PR #91, one day earlier) set the rule — "own tasks lead;
the meter counts own work only" — and applied it to the page, where the split is
visible as the `GrabsTray`. The `chores.today-summary` widget was never touched,
so on the dashboard a kid with one assigned chore and five offers read **"6 tasks
left today"**, with the offers listed among their own rows.

The same list also reached `groupByAssignee` in the family framing, which minted
an "Up for grabs" tile: a spine, an avatar, and a name for something that is not
a person — and it spent one of the list rows auto-bug #70 had fought to get back.

## Fix (PR #97, merged `e85c509`)

All six taskee variants (Agency + Focus × compact/standard/large) count, meter,
and list `assigneeId !== null` only. The all-done and no-tasks states carry a
hearth `N up for grabs` chip, because an unqualified 🎉 over a live board is the
false celebration D6 rejected on the page.

Family framing keeps the count and loses the row — **gated with the user**
against four options (header chip · sunken tray footer · aggregate line · drop it
entirely). Header chip chosen: `groupByAssignee` now skips unassigned tasks
outright, `PersonTile` and `MemberGroup` shed the `upForGrabs` branch so nothing
can mint a person row for unowned work again, and a shared `FamilyTrailing` puts
both household aggregates on the header's trailing edge with overdue outermost.
Unclaimed work still counts in the family hero and meter — it is the household's
work — and the chip is what accounts for the gap between that hero and the sum of
the member chips.

+7 plugin tests (95 green in chores). Reviewed live in the shell as both Zoë
(taskee) and Zach (family) before close-out.

## Worth remembering

A design gate settles a **rule**, not a diff. D6's rule was stated for "both
taskee surfaces" and the page's two got it; the widget is a third surface reading
the same endpoint and nobody swept for it. The endpoint that returns a mixed list
is the thing to grep from — `GET /chores/tasks` has four consumers.

## Closed out

Deployed and verified on prod: the served widget chunk carries the split and the
chip, and `assigneeName ?? "Up for grabs"` is gone from it. Reports `a59e6e5c`
(#94) and `e7374f56` (#92, owed from the prior session) both moved to
**`deployed`** — every report through #94 is now closed.

One process note for the next fix session: `gh run list --limit 1` is not a
deploy signal. `deploy.yml` fires on `workflow_run`, so for minutes after a merge
the newest run is still the _previous_ commit's, already `completed` — a wait
loop exits on it instantly and the stale bundle reads as shipped. Capture the run
id you mean, and confirm against the served chunk regardless.
